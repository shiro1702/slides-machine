Надо учесть еще один флоу рендер картинок на клиенте (дешевле и иногда проще) на сервере рендеринг тоже нужен когда все отладится (на клиенте будем использовать html-to-image) идея такая клиент накидываетс текст когда ему все понравилось то нажимает сгенерировать карусель, ему возвращается ссылка на редактирование ор открывает ее и там его карусель где он может изменить все (по идее в первую очередь картинки, тк в вебе эти сделать проще чем в инлайн режиме бота, и после нажимает кнопку экспорта на сайте и сохраняет зип файл у себя, или делает генерацию на сервере и в ответ бот пришлет сообщение с картинками слайда.

Отличный ход мысли — это правильная гибридная архитектура. Клиентский рендер снимает нагрузку с сервера на этапе, когда деньги ещё не зарабатываются, а серверный остаётся для «автоматического» флоу через бота и будущих рилсов. Разберу детально.

Общая схема флоу
1. Юзер в боте:      накидывает тему/текст, итерирует с AI
2. Бот:              «Готово! → Открыть редактор» (ссылка/Mini App кнопка)
3. Веб-редактор:     preview всех слайдов, правки текста, картинок, темы
4. Экспорт — два пути:

   Путь A (клиент):  html-to-image → ZIP → скачал себе
   Путь B (сервер):  кнопка «Отправить в Telegram» →
                     server render → бот присылает альбом картинок

Ключевая красота: оба пути рендерят одни и те же React-компоненты. Это главный архитектурный принцип, о нём ниже.

Архитектура: один источник правды для рендера
Самая опасная ошибка здесь — сделать два разных рендера (клиентский и серверный), которые со временем разъедутся: в вебе слайд выглядит так, а бот присылает чуть другое. Пользователь этого не простит.
Решение: shared slide components
/packages/slides          ← общий пакет
   /components
      HookSlide.tsx
      NumberedSlide.tsx
      ChecklistSlide.tsx
      ChartBarsSlide.tsx
      ...
   /themes
      tokens.ts           ← темы как CSS-переменные
   renderSlide.tsx        ← type + data + theme → JSX

/apps/web                 ← Next.js на Vercel
   использует @slides для preview и html-to-image

/apps/render-worker       ← серверный рендер
   использует ТЕ ЖЕ @slides через Satori/Playwright/Remotion

Слайд — это чистая функция:
<SlideRenderer
  type="numbered"
  data={{ number: 3, title: "...", text: "..." }}
  theme={clientTheme}
  layout="dark_premium"
  width={1080}
  height={1350}
/>

Где она выполняется — в браузере юзера или на сервере — не важно, результат одинаковый.

Путь A: клиентский рендер (html-to-image → ZIP)
Как это работает
1. В редакторе слайды свёрстаны как DOM-элементы 1080×1350
   (на экране уменьшены через transform: scale)
2. По кнопке «Скачать»:
   - для каждого слайда вызываем toPng(node, { pixelRatio: 1 })
   - складываем PNG в JSZip
   - saveAs("carousel.zip")

Подводные камни html-to-image (важно!)
1. Шрифты: рендерить только после document.fonts.ready
2. Картинки и CORS: Access-Control-Allow-Origin на Blob
3. Скрытые слайды: offscreen-контейнер, НЕ display: none
4. Safari/iOS: toPng дважды, тест на iPhone обязателен
5. Память: последовательно, прогресс «Слайд 3 из 7…»
6. Эмодзи: системные; потом Twemoji

Что клиентский рендер даёт
+ $0 затрат на рендер
+ мгновенный WYSIWYG
+ нет очередей в MVP
+ Vercel functions не тратят лимиты

Путь B: серверный рендер → бот присылает картинки
Когда нужен: флоу без редактора; слабые устройства; автопостинг; рилсы; эталон для Pro.

Реализация: MVP варианты Satori / Playwright / Remotion — см. уточнение ниже (Strategy B = Remotion).

Ссылка на редактирование: auth без регистрации
https://app…/e/{projectId}?t={signed_token}
JWT { userId, projectId, exp } или одноразовый код.
Mini App initData + обычная ссылка для десктопа.

Состояния проекта
draft → generated → editing → exported | rendering → delivered
Источник правды — JSON в Neon, картинки — производный артефакт.

Картинки юзера в редакторе
Web: drag&drop → Vercel Blob client upload → blob URL в JSON.
Кроп: object-fit / object-position. В боте фото — итерация 2.

Экономика
Free: клиентский экспорт ± watermark
Pro: серверный рендер в бота, без watermark
Клиент ~$0; сервер ~1–3с CPU/слайд на дешёвом VPS.

Итоговый порядок (черновик в диалоге, далее скорректирован под Remotion):
Спринт 1: бот JSON, веб /e/{id}, html-to-image ZIP, signed link
Спринт 2: edit текст/порядок/тема, фото Blob, /render page
Спринт 3: server worker, кнопка в боте, sendMediaGroup, аналитика

Итоговая картина:

Путь B — Remotion renderStill (бот / Pro)
Путь C — Remotion renderMedia (рилсы)

Надо учесть в архитектуре проекта что точкой входа может быть бот не только от одного мессенджера, а несколько.

Главный принцип: бот — тонкий адаптер, Core — вся логика.

Adapters (TG / WA / VK / Max) → Core Engine ← Neon · Blob · Remotion · Web

InboundEvent / OutboundMessage — универсальные типы.
Capabilities: Core выражает intent (choose options), адаптер рисует UI канала.

Identity: users + user_identities (channel, channel_user_id).
Проекты/тарифы на users.id. Слияние аккаунтов — не MVP, схема — с первого дня.

dialog_sessions: state machine в Core, тестируется без мессенджеров.
Файлы: адаптер сразу → Blob; Core видит только наш URL.
Доставка: worker → Core → нужный адаптер (TG альбом 10 / WA по одному).

Auth редактора: JWT signed link (везде) + Mini App initData (TG).

Monorepo:
/packages/slides, /packages/core, /packages/db
/apps/web, /apps/remotion, /apps/bot-telegram, (потом WA/VK)

MVP: схема identities + Core interfaces + только TG-адаптер.
НЕ: WA/VK адаптеры, merge аккаунтов, универсальный конструктор диалогов.

Тест кода:
1. Знает про Telegram? → bot-telegram
2. Знает про слайды/тарифы? → core
3. Знает и то и то? → ошибка, разрезать
